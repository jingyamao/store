# 章节历史记忆设计

## 目标

在现有章节初稿、作者确认状态回写和多层上下文之上，补上可查询的历史事实。写任意章节时，Agent 应能知道该章之前已经确认的人物状态、关系、物品和伏笔状态，同时避免把后续章节的状态当成已发生事实。

## 方案选择

1. **沿用已确认的 sync 差量，另存作者手工补录的章节事实（采用）。** 现有提案已经有章节、旧值、新值和正文依据；手工事实只填它覆盖不到或遗漏的历史。迁移成本低，不重复保存自动提取结果。
2. 每章保存完整 Bible 快照。查询简单，但长篇会复制大量数据，手工修改和快照之间容易分叉。
3. 用向量检索替代结构化事实。可以找到相似段落，却不能可靠回答某一章节人物具体持有什么、关系何时改变。

## 数据与规则

- 每章可有 `memory/ch-XXXX.yaml`，保存作者明确确认的事实事件。事件包括实体集合、实体 ID、字段、值、出处类型及依据。正文出处必须能在该章定稿文本中找到；作者说明须明确标为人工依据。
- 第一版支持人物动态状态与关系快照、物品状态、伏笔状态。字段值按现有 Bible schema 校验，拒绝任意路径写入。
- 查询目标章 `N` 时，只能使用章节号小于 `N` 的事件。将已应用的 sync 变化与手工事件合并，对同一字段选择截至 `N` 最近的一条；同章冲突以作者手工记录为准，并给出告警。
- 已确认事件只作为历史层读取，不自动覆盖当前 Bible。若历史与当前卡片不一致，运行记录说明使用了哪条章节事实。原有 Bible 后期快照回推仍作为没有更精确事件时的保守兜底。
- Agent 的 `context.json`、`agent-memory.json` 保存实际进入提示词的来源。作者可用 CLI 查看某章生效的历史事实。

## 使用与验证

命令行提供 `novel memory record <chapter> <collection> <entity> <field> <json-value> --evidence <text>` 和 `novel memory show <chapter>`。记录前完成字段、实体、证据与时间校验；同一章节同一字段只保留一个手工记录，再次记录需要显式覆盖。

测试覆盖：过去/当前/未来事件的可见性；同步差量与手工事件的优先级；人物关系回溯；无效字段及不存在的正文依据被拒绝；生成上下文中的来源可追溯。实书多章节漏检率评测另作为下一项独立工作。
